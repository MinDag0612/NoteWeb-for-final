# CI Evidence Map

This document defines the evidence generated by Phase 2 CI and explains how each artifact maps to the final project rubric, technical report, and live demo flow.

## Scope

This document covers **Step 8** only:

- reproducible CI outputs
- security evidence
- image provenance evidence
- demo-friendly workflow outputs

It does **not** claim that CD, Docker Swarm deployment, domain/HTTPS, or monitoring are already complete.

## Workflow Source of Truth

- Workflow: [`.github/workflows/ci.yml`](../.github/workflows/ci.yml)
- CI branch in progress: `feature/module2-ci`
- Registry contract:
  - `nguyenhongphu1/noteweb-frontend`
  - `nguyenhongphu1/noteweb-backend`
- Primary immutable deployment tag: `sha-<shortsha>`
- Branch traceability tag on branch builds: `branch-<sanitized-branch>`
- Release tag on versioned releases: `vX.Y.Z`

## Evidence Produced by CI

### 1. Frontend Build Artifact

- Artifact name: `frontend-build`
- Produced by job: `frontend-ci`
- Contents: production-ready React build output from `frontend/build`
- Why it matters:
  - proves the frontend build is reproducible
  - provides an auditable artifact for the report
  - can be referenced in demo narration when explaining the build stage

### 2. Repository Security Report

- Artifact name: `trivy-fs-report`
- Produced by job: `security-scan`
- Contents: Trivy filesystem scan report in JSON format
- Scan scope:
  - vulnerabilities
  - secrets
  - misconfigurations
- Why it matters:
  - proves repository-level security scanning is integrated into CI
  - provides raw evidence for the report and screenshots
  - supports the documented risk-acceptance decision for the legacy CRA toolchain

### 3. Image Evidence Artifact per Service

Artifact names:

- `image-evidence-frontend`
- `image-evidence-backend`

Produced by job: `docker-images`

Each artifact contains:

- `<service>-image-metadata.json`
  - image repository
  - immutable `sha-*` tag
  - traceability `branch-*` tag when the source ref is a branch build
  - release `v*` tag when the source ref is a Git release tag
  - Git SHA, ref, workflow, run ID
- `<service>-trivy-image-report.json`
  - machine-readable Trivy image scan report
- `<service>-sbom.cdx.json`
  - CycloneDX SBOM for the built container image

Why this matters:

- proves the exact image version built by CI
- gives strong evidence for image-level DevSecOps integration
- provides machine-readable material for the technical report appendix
- establishes a clean handoff contract for future CD and Swarm deployment

## Rubric Mapping

### Section IV.2.1 CI Requirements

- Code quality and linting:
  - visible in `frontend-ci` and `backend-ci`
- Dependency caching:
  - `actions/setup-node` npm cache
  - `actions/setup-python` pip cache
- Reproducible build artifact:
  - `frontend-build`
- Security scanning with fail gate:
  - `trivy-fs-report`
  - Trivy image gate in `docker-images`
- Container build and registry push with explicit tags:
  - `sha-*`, `branch-*`, and `v*` tags recorded in image metadata according to the source ref

### Section IV.5 Documentation and Evidence

- JSON reports support appendix evidence and screenshots
- SBOM files support traceability and dependency transparency
- Step summaries in GitHub Actions make demo logs easier to read live

## Demo Mapping

### Section V.3 CI Pipeline Execution

Show these workflow outcomes:

- frontend lint, test, and build completed
- backend lint and tests completed
- repository security scan completed
- image build completed for both services
- image scan evidence generated
- immutable image tags generated
- branch pushes validate image creation without publishing feature-branch artifacts
- `push` to `main` publishes `sha-*` and `branch-main`
- release tags such as `v1.2.0` publish `sha-*` and the matching `v*` release tag

### Section V.4 Delivery Preparation

Even before CD is added, the CI artifacts already prove:

- which exact image version should be deployed
- how production should consume the immutable `sha-*` tag
- that deployment metadata is machine-readable and reproducible
- that release-style tags can be published without changing the primary `sha-*` deployment contract

### Section V.5 Verification Support

When CD is implemented later, the same metadata artifacts should be used to show that the deployed image version matches the CI-produced `sha-*` tag.
